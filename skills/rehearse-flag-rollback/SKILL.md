---
name: rehearse-flag-rollback
description: Use the Flagsmith CLI to rehearse a flag rollback against fresh and in-flight application work, compare rollback policies, and report which application invariants hold.
---

Use this when turning a flag off (or back on) could strand work started under its previous assignment. A successful flag write establishes configuration state. Only a probe of the application can establish what happens to that work.

1. **Define the decision.** Identify the project, environment, flag, before/after assignment, audience, and candidate retirement policies. Ask what must stay true for a new visitor and for work already in progress. Phrase each check as something you can observe. Can the user reopen a saved draft? Does a retried job deliver exactly once? Agree on required checks before inspecting results.
2. **Find the application probe.** Look for an existing integration test or fixture. Adapt it to the [probe contract](references/probe.md) if needed. Confirm equivalent work completes before the rollback. Capture one piece of synthetic work and replay independent copies with the same dependencies and inputs under each candidate policy. Sample the actual application outcome, including side effects. If the necessary fixture or observation is unavailable, report the missing evidence.
3. **Confirm scope.** Identify both API origins and the numeric project ID with the operator. Establish permission to create and remove a disposable clone and to run the selected application fixture. Use staging dependencies and an authorized credential for that instance. Review the probe before running it. Flag isolation alone does not isolate queues, databases, payments or webhooks.
4. **Run the rehearsal.** Run the helper from the installed skill directory, using Flagsmith CLI v2, Flagsmith 2.263.0 or newer, Python 3 and an executable probe (the example uses a POSIX shebang). The helper reads the source, creates a uniquely named clone, checks the environment default and the SDK assignment before capture and after the change, then runs the named plans and verifies clone removal. The source receives no flag writes. Pass the application's own check names and policies. For an executable local example, see the [queue rehearsal](references/probe.md#try-the-queue-example).
5. **Report the decision.** Read the compact JSON receipt and exit code. Name the audience, failing or unobservable invariants, and cleanup status. Recommend a plan only after its required checks pass and cleanup is verified. A mixed comparison exits 1 even when one plan passed. If cleanup is unverified, resolve the run's generated name to its ID and verify ownership before removal. If interrupted by a hard kill, use the name printed before cloning. Never retry a mutation blindly.
6. **Hand off the release.** State which traffic, versions and dependencies were exercised. Report missing evidence or unverified cleanup before recommending any action. For additional audiences run separate rehearsals using synthetic identities and known traits. Cloning omits identity-specific state. Applying anything to a shared or production environment requires a separate decision. Present the proposed change, re-read current state and obtain explicit approval. A rehearsal does not establish production-wide safety.

The helper changes the environment default's Boolean state. For a value, variant-weight or override rollback, rehearse that exact scope in a disposable environment with the CLI and evaluate the relevant identities and values. Do not substitute a Boolean toggle as evidence for a different change.
